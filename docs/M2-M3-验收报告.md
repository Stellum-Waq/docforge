不用改 UI 框架。UI 读取 `params_schema` 即可自动生成参数表单。

### 1.2 为什么预览放在内核而不是前端

"所见即所得"的前提是预览与真实输出**出自同一套代码**。如果前端用 Canvas 复刻一遍
排版逻辑，两边的字体度量、描边算法、旋转插值只要有像素级差异，用户就会陷入
"预览好看、结果不对"的反复试错。

所以预览的做法是：把原图按比例缩小，用**完全相同的动作代码**渲染一遍。参数全部是
相对比例（字号/边距占短边百分比），因此缩略预览与全尺寸输出在视觉上一致。

### 1.3 Electron 侧

新增 `main/sse.ts`（手写 SSE 解析 + 自动重连）、任务 IPC 转发、二进制预览转 data URL、
命令行/文件关联传入文件。

## 3. 本轮发现并修复的真实缺陷

这些都是**只有真跑起来才会暴露**的问题，也是本轮最大的价值所在。

### 3.1 【严重】输出格式判定顺序错误 → 崩溃

**现象**：透明 PNG 转 JPEG 时崩溃 `cannot write mode RGBA as JPEG`。

**根因**：先按**源扩展名**判断"是否要拍平透明通道"，之后再按**输出扩展名**切换保存
格式。两步顺序反了，就会出现"判定为 PNG 所以不拍平，却按 JPEG 保存"。

**修复**：**先定死最终格式，再决定拍平**。并加了两条回归测试锁住行为。
这个 bug 用户必然遇到（谁都会想把 PNG 转成 JPEG），属于必修项。

### 3.2 【严重】命令行参数位置切片错误 → 递归扫描整个项目

**现象**：只传了 5 个图片路径，工作区却出现 **37 个文件**。

**根因**：用 `argv.slice(2)` 假定"跳过 application path"，但 Chromium 开关
（如 `--remote-debugging-port`）位置不固定，切片错位后 `.` 被当成待处理目录，
**递归扫描了整个 apps/desktop 目录**。

**修复**：放弃位置切片，改为语义判断 —— 跳过开关、跳过 `app.getAppPath()`、
只接受真实存在的路径。位置切片本身就是脆弱设计，已加注释警示。

### 3.3 【严重】路由切换依赖退出动画 → 界面"点不动"

**现象**：点击侧边栏后按钮已高亮（状态确实变了），但主内容区不更新。

**根因**：`AnimatePresence mode="wait"` 要求新页面**等旧页面退出动画播完**才挂载，
而退出动画依赖 `requestAnimationFrame`。当窗口被其他程序完全遮挡时，Chromium 会把
页面标记为 `hidden` 并**完全暂停 rAF** —— 动画永远播不完，导航就此卡死。
实测确认：`visibilityState: "hidden"`，800ms 内 rAF 一帧都没跑。

**修复**：路由只做入场动画，不依赖任何可被节流的东西。视觉几乎无差别，但切换变可靠。

### 3.4 【中】渲染进程在内核就绪前调用接口 → IPC 抛错

**现象**：内核启动中的 IPC 报错 `内核尚未就绪`，活跃任务加载失败。

**修复**：只读查询改为返回空而不是抛错（抛出去会变成渲染进程的未处理 rejection）；
内核就绪后由前端主动补拉一次。

### 3.5 【中】开发模式把结果写到用户真实桌面

**现象**：调试时产物落在 `C:\Users\<用户>\Desktop\DocForge输出`。

**修复**：显式指定 `DOCFORGE_DATA_DIR` 时（开发与自动化测试都会这么做），
输出跟随数据目录，不再污染用户桌面。生产运行时才用桌面。

### 3.6 【中】UI 缺输出目录选择器

**现象**：用户无法决定结果存哪 —— 这是"文件转换工具"的基本诉求。

**修复**：内核在能力探测里返回建议的默认输出目录，界面上提供可编辑的路径 + 目录选择按钮。

### 3.7 【方法论】用截图 + SendKeys 验证桌面应用是危险做法

**事故**：为切到指定页面，用 `SetForegroundWindow` + `SendKeys` 发 Tab/Enter。
但 `SetForegroundWindow` 并未生效，按键**打进了用户当时正在用的微信**（打开了一个聊天），
而且抓屏抓到的是微信窗口，导致第一次「视觉验证」的结论完全是错的。

**改正**：改用 **Chrome DevTools Protocol**（`tools/cdp.mjs`）直接驱动渲染进程。
优点：只能操作本应用、不受窗口遮挡影响、可精确读写 DOM、不会误伤其他程序。
这个方法上的教训值得记住 —— 验证手段本身不能有副作用。

## 5. 下一步：M4（OCR 双引擎）

这是需求 2 与需求 8 的核心，也是技术风险最高的一块：

1. **本地引擎**：接入 RapidOCR（ONNX，离线，无需 PyTorch），跑通"图片 → 文字"
2. **云端引擎**：接入 DeepSeek Vision（`deepseek-flash`），实现
   **自适应切片 OCR** —— 本地做版面分析 → 语义切块（带重叠）→ 并发识别 →
   坐标回贴 + 重叠去重。这是应对官方"单图 1024 token 上限导致密集小字丢失"的关键
3. **图片 → Excel**：识别表格结构 → `openpyxl` 生成带样式的 xlsx
4. **引擎路由与降级**：断网自动切本地；敏感文件强制本地
5. **成本控制**：结果哈希缓存（重复文件零计费）+ 实时用量面板
6. **设置页**：API Key 用 Windows DPAPI 加密存储
