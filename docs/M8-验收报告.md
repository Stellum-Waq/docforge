卸载时保留用户数据（`deleteAppDataOnUninstall: false`）。

### 1.2 内核打包（PyInstaller onedir）

选 onedir 而不是 onefile：onefile 每次启动都要把几百 MB 解压到临时目录，
冷启动要十几秒；onedir 就地加载，实测启动 **3–9 秒**。

spec 里有三处必须显式声明的收集项，少一个都会导致"装出来才是坏的"：

| 收集项 | 不收集的后果 |
|---|---|
| `rapidocr_onnxruntime` 的包数据 | ONNX 模型不在包里 —— 程序能启动，一用 OCR 就报找不到模型 |
| `uvicorn` 的 loop / protocol / lifespan 实现 | 动态导入，静态分析看不到，内核根本起不来 |
| `win32com` / `pythoncom` / `pywintypes` | COM 自动化全靠运行时动态导入 |

排除项（tkinter / Qt / matplotlib / Jupyter / torch 等）用于压体积。

### 1.3 首次启动自检

新增 `GET /api/system/selfcheck`，三档状态回答用户最关心的问题 ——
**"我这台机器上它能干什么？"**：

* `ok` 该能力可用
* `warn` 可选能力缺失，**功能降级但仍可用**
* `fail` 关键能力缺失，相关功能不可用

文案上刻意区分"降级"与"错误"：没有 Office 不代表软件坏了，只是保真度低一些；
把这种区别讲清楚，用户才不会以为装了个残缺的东西。每个非 ok 项都附带
**"影响"**说明，而不是只丢一句"不可用"。

界面上有两处入口：首次启动的向导（只弹一次），以及总览页与设置页里可随时重跑的面板。

### 1.4 应用图标

用代码生成（`tools/make_icon.py`）而不是塞一张位图：配色跟着设计令牌走，
改一个数值就能重新出一套全尺寸图标。包含 16/24/32/48/64/128/256 七种尺寸 ——
Windows 会在任务栏、开始菜单、文件关联等不同场景选取不同尺寸，
只给一张 256 会被强行缩放而变模糊。

## 3. 本轮发现并修复的缺陷

### 3.1 【严重】打包后新增的接口直接 500

**现象**：打包后的内核访问 `/api/system/selfcheck` 返回 500，开发环境却正常。

**根因**：PyInstaller 在**分析阶段**抓取源码，而我在它已经开始分析之后才补上
`routes.py` 里缺失的 `Path` 导入 —— 产物里是一份过时的源码。

**教训（已写进 README）**：内核源码改动后**必须重新执行打包**，
且打包完必须跑 `tools/test_packaged.py`。这类问题在源码运行时完全不可见。

### 3.2 【严重】关闭应用会泄漏 WINWORD.EXE（三层嵌套根因）

M6 已修复并记录，本轮打包验证再次确认有效。

### 3.3 【严重】"承诺了却做不到"的三处能力不一致

这一类问题很隐蔽：**功能看起来正常，只是什么都没发生。**

| 问题 | 表现 | 根因 |
|---|---|---|
| HEIC 支持 | 打包后自检显示"降级"，拖入 iPhone 照片没反应 | `pillow-heif` 只在运行时被注册、没有静态 import，PyInstaller 不会收集它 |
| pypdf 引擎 | 引擎矩阵里列着"加密/权限/页面级操作" | 装了但**没有任何代码 import 它** —— 纯粹是空头承诺 |
| 图片水印的 HEIC | 后端支持、界面却把 HEIC 当成"不是图片" | `ImageWatermark.tsx` 硬编码了一份扩展名白名单，与动作的 `accepts` 不一致 |

三处都修了：内核启动时统一注册 HEIF 打开器并加进 hiddenimports；
从引擎矩阵移除未被使用的 pypdf；界面改为**完全以动作元数据 `accepts` 为准**，
不再自己维护第二份清单。

### 3.4 【严重】测试断言太弱导致的**假通过**

`test_packaged.py` 里原本这样检查 HEIC：

```python
check(heic_job.get("status") == "succeeded", "HEIC 可处理")
```

问题是：**当文件因格式不匹配被跳过时，任务状态同样是 `succeeded`**
（0 成功 + 1 跳过）。于是这个断言在 HEIC 完全没被处理的情况下依然通过 ——
它替一个真实的缺陷打了掩护。

修复：新增 `job_all_files_succeeded()`，**逐个检查文件级状态**，
不通过时把具体文件与原因一并打印。这条经验适用于所有批量任务的断言。

### 3.5 【严重】可关闭浮层在窗口被遮挡时关不掉

**现象**：点击"开始使用"后，localStorage 标记已正确写入（逻辑是对的），
但弹窗纹丝不动，挡住整个界面。

**根因**：`AnimatePresence` 的退出动画依赖 `requestAnimationFrame`，
而窗口被遮挡时 Chromium 会把页面标记为 hidden 并**完全暂停 rAF** ——
动画永远播不完，元素就一直留在 DOM 里。与 M2 里路由切换卡死是同一类问题，
当时只修了路由，浮层没修。

**修复**：**所有可关闭浮层都不再依赖退出动画** —— 只保留入场动画
（观感上的"高级感"主要来自出现的那一刻）。涉及首次启动向导、
任务中心抽屉、提示条。视觉几乎无差别，但关闭一定生效。

### 3.6 上游依赖缺陷：electron-builder 完全无法打包

**现象**：`electron-builder` 一执行就崩：
`Cannot read properties of undefined (reading 'ReadWrite')`。

**根因**：`app-builder-lib@26.15.x` 的 `electronGet.js` 引用了 `@electron/get`
的 `ElectronDownloadCacheMode` 导出，但它自己声明的依赖范围是 `^3.0.0`，
而那个版本里并没有这个导出。结果是**任何工具链下载都会崩**
（Electron 本体、NSIS、winCodeSign 全中），打包完全走不下去。
查证过 26.15.4 到 26.16.1 全部版本，依赖声明都是 `^3.0.0`，升级解决不了。

**修复**：用 `pnpm patch` 打了一个**可持久化**的补丁
（`patches/app-builder-lib@26.15.3.patch`，配置在 `pnpm-workspace.yaml` 的
`patchedDependencies`），只在枚举缺失时退回等价数值，不改变原有行为。
同时用 `electronDist` 复用已装好的 Electron 二进制，省掉一次几百 MB 的重复下载。

> 注：pnpm 11 起 `patchedDependencies` 等设置从 package.json 的 `pnpm` 字段
> 搬到了 `pnpm-workspace.yaml`，写错位置只会得到一句警告然后被忽略。

### 3.7 扫描件判定误伤稀疏文本页

**现象**：只有一行标题的封面页被判定为"扫描件"，提示用户"请先做 OCR"。

**根因**：判据只看"每页平均文字少于 20 字"。

**修复**：扫描件的真实特征是**文字少且有图**，加上图片数量条件后误判消失，
并补了回归测试。

### 3.8 首次启动向导报"内核尚未就绪"

打包后内核冷启动要 8 秒，而自检面板在此之前就挂载了。原本失败后不再重试，
用户看到的是一个红色错误框。修复：识别"尚未就绪"为**预期状态**并自动重试
（最多约 30 秒），期间显示"正在等待处理内核启动…"，同时提供手动重试。

## 5. 已知限制（如实说明）

1. **云端 OCR 引擎未经真实 API Key 联调**。本机无密钥，请求构造、JSON 解析、
   错误分类、降级逻辑均按官方文档实现并有测试覆盖，但**没有跑过真实调用**。
   这是目前最主要的验证缺口。
2. 扫描件 → **双层可搜索 PDF** 尚未实现（OCR 能力已就绪，差一层封装）。
3. PDF 加密 / 解密 / 权限设置尚未实现。
4. 表格合并单元格（`spans`）尚未应用到 xlsx。
5. 渲染产物 1.39 MB 未分包（对桌面应用影响有限，但接入 PDF 预览器前应处理）。
6. 未安装 LibreOffice 的环境下，Excel/PPT 转 PDF 只能依赖 Office COM 或报错
   （内置渲染不做 xlsx/pptx，因为靠文字提取没有意义）。
