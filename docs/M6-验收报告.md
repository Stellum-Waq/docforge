# M6 验收报告 — PDF ↔ Word 与 Office 转换

> 日期：2026-09-11 · 状态：**通过** ✅ · 累计进度：M0–M6 ✅

本轮交付**需求 3（PDF 和 word 转换）**，并顺带完成了 Word/Excel/PPT → PDF 的完整引擎路由。

---

## 1. 交付内容

### 1.1 三级引擎路由

Office / 文档 → PDF 按**保真度**择优，不可用时逐级降级：

| 优先级 | 引擎 | 保真度 | 实测状态 |
|---|---|---|---|
| 1 | **Office COM** | 100 | ✅ 本机可用（Word / Excel / PowerPoint 全部就绪） |
| 2 | LibreOffice headless | 82 | 未安装；实现完成，安装后自动启用 |
| 3 | 内置渲染（纯 Python） | 55 | ✅ 永远可用，保证功能不会彻底失效 |

**为什么第三级值得实现**：没有 Office 也没有 LibreOffice 的机器（干净的服务器、
部分企业终端）上，若直接报"功能不可用"，用户会觉得软件是坏的。内置渲染虽然
不保留精确版式，但能把文字与基本结构带过去 —— 对"我只想要内容"的场景已经够用。

反向转换 **PDF → Word** 用 `pdf2docx` 还原版面；检测到扫描件（文字层为空）时
**提前给出可读指引**，而不是让用户拿到一个空白 Word 再困惑；用户勾选
「扫描件自动 OCR」后，会先走本地 OCR 再重建文档。

### 1.2 COM 自动化的三个工程要点（都真踩过）

**① COM 是 STA（单线程套间）。** 对象只能在创建它的线程上使用。给每个 Office 应用
配了一条**专用工作线程**，所有调用排进它的队列串行执行。

**② Office 进程会卡死。** 弹出宏安全对话框、等待用户输入都会让调用永久挂起，
因此每个调用都带**看门狗超时**，超时后强杀并重建。

**③ 强杀时绝不能误杀用户自己打开的文档。** 做法是：创建 COM 对象**之前**先记录该进程的
现有 PID，之后只清理"新出现的"那些。验证过程中本机确实有一个用户自己的 Excel 在跑
（PID 14248，启动于 08:22，远早于我的测试），**全程未被触碰** —— 这条约束真的起了作用。

### 1.3 动作模型：聚合动作从元数据暴露

`ActionInfo.aggregate` 现在通过 `/api/actions` 暴露，界面据此决定交互
（只建一个任务、不显示并发数），而不是在前端硬编码"哪个 id 是合并"。

### 1.4 界面

- **文档转换页**：文档转 PDF / PDF 转 Word，参数表单由后端 `paramsSchema` 生成
- 抽出可复用的 `ToolWorkbench` 组件，PDF 工具箱与文档转换页共用
- 候选文件列表**跟随所选工具的 accepts 过滤**（见 §3.2）

## 3. 本轮发现并修复的缺陷

### 3.1 【严重】关闭应用会泄漏 WINWORD.EXE

这是本轮最有价值的发现，也是最容易在生产环境被投诉的问题。

**现象**：通过界面正常关闭应用后，Word 进程仍然活着 —— 用户看不到窗口、
进程却占着几百 MB 内存，还可能锁住文档导致下次转换失败。

**排查过程**（三层根因层层嵌套）：

1. **第一层**：Electron 停止内核用 `proc.kill()`，在 Windows 上等于
   `TerminateProcess` —— Python 的清理代码**一行都不会执行**。
   → 修复：新增 `POST /api/shutdown` 优雅退出接口，Electron 先请求、
   等 8 秒才强杀；父进程看门狗也从 `os._exit` 改为"先清理再退出"。

2. **第二层**：`Quit()` 抛 Windows 级异常（`0x800706be`）时，
   `_kill_owned_processes()` 被跳过 → 进程泄漏。
   → 修复：把清理放进 `finally`，并给 `shutdown_all` 加第二层 `force_kill` 兜底。

3. **第三层（最隐蔽）**：COM 工作线程是**守护线程**，主进程退出时会被直接掐断。
   清理逻辑只在它里面跑，一旦被截断就什么都清不掉。
   → 修复：`shutdown()` 不再依赖工作线程完成清理，join 之后由**调用线程**
   再执行一次强制清理（`_quit_app(gentle=False)`）。

顺带修掉的两个相关缺陷：
- `DispatchEx` 返回时 Office 进程可能**还没出现在进程列表里**（Word 冷启动要一两秒），
  导致 `_owned_pids` 采集为空、无从清理 → 改为轮询等待进程出现
- 单次 `kill()` 的返回值不可信（实测遇到过进程正在退出时 `psutil.Process(pid)` 抛
  `NoSuchProcess`，集合被清空却什么都没杀掉）→ 改为"调用 → 验证是否真的消失 →
  重试 → 仍不行降级到 `taskkill /F /T`"

### 3.2 候选文件列表没有跟随所选工具过滤

选「文档转 PDF」时，工作区里的 PDF 仍然列在待处理列表中，执行后被跳过并提示
"该任务不接受 .pdf 格式的文件"。功能是对的，但体验像是在报错。
→ 修复：候选列表按当前动作的 `accepts` 过滤，并给出清晰说明。

### 3.3 扫描件 OCR 路径传了 `BytesIO`

`recognize()` 需要文件路径（要用它做缓存键、敏感名匹配、版面分析），
传入内存字节流会失败；异常被 catch 成空文本，最终产出一份**空白 Word**。
→ 修复：先把渲染页面写入临时 PNG 再调用，并在全程无文字时给出明确错误。

### 3.4 测试自身的两处错误

- 断言"转换后立刻没有 Word 进程" —— 但工作线程**刻意复用**同一实例
  （每次重启要 1–3 秒），转换刚结束时它本来就该活着。改为在**内核退出后**检查。
- 基线与终检统计的进程类型不一致（一个只数 Word、一个数三类），
  导致用户自己的 Excel 被误报为泄漏。
