## 1. 交付内容

### 1.1 自适应切片（本功能的技术核心）

DeepSeek Vision 在推理前会把图片缩放到"约 1300×1300 等效像素"、单图上限 1024 token。
一张 4000×3000 的密集文档被缩放 2.66 倍后，原本 12px 的字只剩 4.5px —— 根本认不出来。

因此本轮的算法核心是 `docforge/ocr/tiling.py` 的切片规划。设文字行高为 `h`，
模型对边长 `L` 的切片缩放 `s = 1300/L`，要求缩放后行高不低于可读阈值 `MIN_LINE_PX`：

```
h · (1300 / L) ≥ MIN_LINE_PX   →   L ≤ 1300 · h / MIN_LINE_PX
```

结论很符合直觉，也纠正了一个常见误解：

| 场景 | 行高 | 推导出的切片上限 | 结果 |
|---|---|---|---|
| 300 DPI A4 扫描件（2480×3508） | ~42px | 4550 | **整图一次识别**，无需切片 |
| 4000×3000 密集文档照片 | ~12px | 1300 | 切成约 4×3 块 |

**不是"图大就切"，而是"字小才切"。** 盲目按固定网格切图既慢又贵，
还会因为切断文本行而降低准确率。

跨切片合并用"核心区归属"去重：每块切片划出不带重叠带的核心区（对全图无缝划分），
每个文字块归给"它最居中"的那块切片，重叠带里的重复自然消除；
再用"位置邻近 + 文本互为包含"做兜底聚类（后者专门处理被切片边缘裁断的半行字）。

### 1.2 本地离线引擎（默认）

- **RapidOCR + ONNXRuntime**，完全离线、零费用、文件不出本机
- 模型随包分发，装完即可用，**不需要首次运行时联网下载**（企业内网关键）
- 推理用模块级锁串行化：ONNX 会话不是为并发设计的，而队列用的是线程池
- 读图走 PIL 而非 `cv2.imread`，从而支持 HEIC（iPhone 照片）并按 EXIF 摆正方向

> **选型过程中的一个坑**：先试了较新的 `rapidocr` 3.9.2，它依赖 `omegaconf`，
> 而后者要求 `antlr4-python3-runtime==4.9.*`，国内镜像只镜像了 4.11+，
> 导致 pip 回退到 2020 年的 omegaconf 2.0.0，启动即抛
> `UnsupportedValueType: WindowsPath is not a supported primitive type`。
> 最终改用成熟的 `rapidocr-onnxruntime` 1.4.4 —— 无 omegaconf 依赖、模型内置，
> 对桌面软件更合适。

### 1.3 云端引擎（DeepSeek Vision）

严格按[官方文档](https://api-docs.deepseek.com/guides/vision)实现：

| 项目 | 实现 |
|---|---|
| 模型 | `deepseek-flash`（**唯一**支持 Vision 的模型） |
| 图片传法 | Base64 `data:` URL，PNG 优先、超 8MB 时转高质量 JPEG |
| 结构化输出 | `response_format={"type":"json_object"}`（提示词含 "json"） |
| 重试 | 401/402/403/400 不重试直接给可读原因；429/5xx 指数退避重试 3 次 |
| 并发 | 全局信号量限制本机并发，切片之间用线程池并行以缩短总耗时 |
| 成本控制 | 结果缓存（文件内容哈希 + 提示词版本 + 参数）+ 用量与费用统计 |

### 1.4 两条图片转 Excel 路径

| 引擎 | 方式 | 特点 |
|---|---|---|
| 云端 | 提示词要求返回结构化 JSON 表格 | 能识别合并单元格，复杂表格最准 |
| **本地** | `ocr/table.py` 从文字框坐标**几何重建** | 完全离线、零费用 |

本地重建的找列算法值得一提：把每个文字块的横向区间投到坐标轴上统计覆盖率，
**覆盖率为 0 的连续区段就是列间隙**。这比"按 x 中心聚类"稳健得多 ——
同一列里短文本和长文本的中心可以差很远，但只要没有别的单元格插进来，
覆盖法就不会把它们判成两列。

### 1.5 界面

- **由 JSON Schema 自动生成参数表单**：新增功能只需在后端声明参数，前端一行都不用改
- **"先试一张，满意再批量"**：单张试识别实时回显文本、置信度、切片数、耗时与花费，
  避免批量跑完才发现参数不对（云端模式下还会白花钱）
- **设置页**：引擎状态、API Key（掩码显示 / 保存 / 测试连接 / 清除）、
  敏感文件名规则、用量与费用、缓存管理

### 1.6 密钥安全

API Key 使用 **Windows DPAPI**（ctypes 调用 `crypt32.dll`）加密存储，零额外依赖。

> 设计文档原本写的是 Electron `safeStorage`。两者底层都是 DPAPI，安全性等价，
> 但实际使用密钥的是 Python 内核 —— 由 Electron 保管意味着**每次调用云端都要把
> 明文密钥经 IPC 传一遍**，反而扩大暴露面。改为内核直接加解密后，
> 明文只在真正要用它的那一瞬间存在于内存，Electron 侧完全不需要知道密钥内容。

## 3. 本轮发现并修复的缺陷

### 3.1 【严重】Excel 静默丢失数据

**现象**：一张含 4 行文字的文档图转 Excel 后只剩 3 行，**标题行凭空消失**。

**根因**：表头猜测返回了第 1 行（文档正文常被误判成表头），
而代码用 `rows = grid.rows[header_index + 1:]` 把表头**之前**的行全部丢弃了。

**修复**：改成"先完整写入全部行，再对指定行套表头样式"。
`_write_sheet` 现在接收**完整的行列表 + 表头行号**，而不是拆开的两份。
**契约是绝不丢弃任何一行** —— 静默数据丢失是最难排查的一类 bug，
用户只会发现文件里少了几行，却完全不知道原因。

### 3.2 【严重】并发任务输出路径竞态

**现象**：连续提交两个同名文件，只产出 1 个结果。

**根因**：输出路径只靠 `Path.exists()` 判断。并发处理时，多个同名文件
（例如从不同文件夹拖入的多个「扫描件.png」）会**同时**算出同一个名字，
后写的静默覆盖先写的 —— 用户莫名少文件，且没有任何报错。

**修复**：把"解析路径"与"占用路径"合并为原子操作（进程内预定集合 + 锁），
并在任务结束时释放（失败/取消释放以便重试拿回干净文件名）。
新增两条回归测试锁住行为。

### 3.3 找列算法间隙测量错误

**现象**：所有列被并成一列。

**根因**：间隙被记录在"进入区间"的时刻而不是"离开区间"的时刻，
导致测出的长度恒为 0。

**修复**：改为在覆盖率归零时开始记录间隙、在重新进入区间时闭合。

### 3.4 `always` 切片模式形同虚设

字号较大时，由字号推导的切片上限超过了整图尺寸，`always` 模式仍产出 1×1 切片。
修复：该模式下额外限制到至少 2×2。

### 3.5 其他

- `Workbook.create_sheet(name=...)` 参数名错误（应为 `title`）
- 开发模式默认输出目录会写到用户真实桌面 → 改为跟随数据目录
