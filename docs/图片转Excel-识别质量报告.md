## 零、第二轮：用户那张图为什么一个字都提取不出来

用户给了一张手机整屏截图（1264×2800），跑「图片转 Excel」两次都显示"成功"，
但结果是空的。用它复现后抓到原始响应：

```
finish_reason = length
completion_tokens: 8192
completion_tokens_details: {'reasoning_tokens': 8192}   ← 全部被"思考"吃掉
content 长度 = 0 字符
```

**`deepseek-flash` 是推理模型：它先"思考"再作答，而思考 token 也算在
`max_tokens` 里。** 表格模式要求严格的 JSON 结构，模型会"想"得特别久 ——
实测同一张图：

| 模式 | 思考 tokens | 8192 预算够不够 |
|---|---|---|
| 纯文字 | **240** | 够（6 秒出结果） |
| 表格（强制 JSON） | **7284 ~ 10885** | **被吃光，content 为空** |

也就是说：**8192 的预算 100% 被思考用尽，一个字都没留给回答。**
而代码把"空内容"当成正常返回 → 解析 JSON 失败 → 降级为纯文本 →
纯文本也是空的 → 最终静默交付一个空结果。

### 修复

1. **默认输出预算 8192 → 32768。** 关键是：**预算是"天花板"，不是"花费"** ——
   模型答完就停。实测把上限从 16384 提到 32768，实际输出仍然只有约 12900 tokens，
   费用一分没多。反过来，给低了会直接把结果毁掉。
2. **显式处理 `finish_reason == "length"`**：翻倍预算重试（8192 → 16384 → …），
   一路到 65536；仍然截断就**报错**，绝不返回空内容。
3. **空内容一律报错**：一次调用返回空，不再静默降级成"这张图没有内容"。

### 同一条图上的三种模式对比（修复后）

| 模式 | 结果 | 耗时 |
|---|---|---|
| 表格 + 自动切片 | ✅ 1 张表 / 63 行 / 表头与内容完整 | 34s |
| 表格 + 不切片 | ✅ 1 张表 / 63 行 | 58s |
| 纯文字 | ✅ 79 个文本块 / 1074 字 | 5.7s |

抽出来的表头与内容：`区队 / 班 / 男 / 女 / 姓名 / 房间号`，
`1连 1班 11 0 杨卓 218 关荣升 220` ……
**和用户在 DeepSeek 网页版拿到的结果一致。**

### 顺带修掉的误报

用户截图里那条吓人的警告「字号偏小（缩放后字形约 9px，低于可靠的 15px）」
其实是**误报** —— 同一次识别的结果是完全正确的。

原因是"检测框高度 → 字形高度"的换算系数取 0.6，而它是拿"表格里跨行框被合并"
的样本标定的；手机截图这类行距宽松的内容，框高本身就接近字形高度，
乘 0.6 会系统性低估。**误报会消耗用户对警告的信任**，所以改成 1.0
（`estimate_line_height` 已经用低分位挑出了单行框）。

另外"已裁掉四周空白"以前每张图都会写进任务摘要，现在只在裁掉 ≥15% 时才提示 ——
它本来是个成功的优化，不该占着摘要的位置把真正的警告挤掉。

## 一、第一轮：四个结构性成因

### 1. 本地行高检测**永远返回 0 个框**（最严重的隐藏缺陷）

RapidOCR 在纯检测模式（`use_rec=False`）下返回的是**裸多边形**
`[box, box, ...]`，而代码按 `(box, text, score)` 三元组去解析 ——
解析出来的"文本"其实是坐标点，随后被当成非法数据丢弃。

后果：`detect_lines` 恒返回空列表 → 行高退回"按图高猜"的公式 →
`max(6.0, 354×0.012) = 6px`。而**行高是切片决策的唯一输入**，
于是整套"自适应切片"一直在用瞎猜的数字做决定。

这条链路断了**不会报错**，只会安静地把结果做坏，所以能潜伏很久。

### 2. 小图被判成"字太小"，被竖着切成两半

一张 784×354 的干净表格，因为上面那个 6px 的假行高，被判定"字号极小"，
于是**竖着切成 2 块**。表格从中间劈开：每块只剩 3 列，
"四季度""全年合计"两列整列丢失，同一张表还变成了两张工作表。

讽刺的是：这张图的缩放比例是 **1.00** —— 模型根本不会缩小它，
切片除了破坏结构之外没有任何收益。

### 3. 跨切片的表格片段被当成多张表

每一块都返回"自己的那张表"：表头相同、行不同，重叠带那几行还重复。
原来直接把它们堆进结果列表，用户拿到的是好几张同名工作表，内容互相重复。

### 4. 数值格式丢失 / 货币列退化成文本

- `1,250` 被转成数字 `1250` —— 值对了，但千分位没了；
- `¥128,600.00` 因为带货币符号转换失败，**留成了文本**，那一列无法求和。

两种表现用户都会说"结果不理想"。

## 二、对应的六项改动

| # | 改动 | 位置 |
|---|---|---|
| 1 | 修 `detect_lines` 的输出结构兼容（裸多边形 / 三元组都支持） | `ocr/local.py` |
| 2 | **模型不会缩小图片时绝不切片**（缩放比例是算出来的，不会错） | `ocr/tiling.py` |
| 3 | 表格只做**横向切分**，保住列结构；多片段按表头合并、接缝去重 | `ocr/tiling.py`、`ocr/table.py` |
| 4 | **裁掉四周空白**：把分辨率还给正文（去低频照明做背景估计） | `imaging.py`、`ocr/deepseek.py` |
| 5 | 行高估计改自适应分位数（表格跨行框会让中位数高估一倍） | `ocr/tiling.py` |
| 6 | 数值进 Excel 的同时套上匹配的显示格式 | `actions/image_table.py` |

### 第 4 项是收益最大的一项

模型按**整图**决定缩放比例，所以空白边距会直接吃掉正文分辨率：

```
远距大图切片   2400×3200 → 901×1080    缩放 0.41 → 1.00   去掉 87% 空白
手机拍A4      3000×4000 → 1340×1824   缩放 0.33 → 0.71   去掉 80% 空白
```

裁边后这两张图**不再被缩放**，文字以原生分辨率送进模型，
准确率从 55% / 96% 变成 96% / 100%。

裁边的实现有两个坑，都是实测踩出来的：

* 用"边框颜色中位数"当背景 → 手机照片的光照渐变让空白区域也"偏离背景"，
  只裁掉两成，等于没裁；
* 改成"逐行取各自中位数" → 渐变在同一行内也变化，整行仍被判成内容。

最终用**去低频照明**：把图缩到长边约 96px 再放回来得到照明估计，
相减后只剩锐利的内容。另外要求"足够多的像素同时偏离"才算有内容 ——
否则传感器噪点会让整行空白被判成内容（实测因此只裁掉 4%）。

## 三、用数据说话：为什么阈值这样定

### 行高为什么不用中位数

26 行表格的检测框高度分布实测为：

```
最小 34   p10 42   p25 70   中位 94   p75 118   实际行距 42
```

中位数 94 是真实行距的 **2.2 倍** —— 因为表格行距紧，检测框把相邻两三行并成了一个。
所以改成自适应：分布很紧用中位数（正文文档），分布松散用 p10（表格）。

### "结果可能不准"的提醒门槛

同一张图重复识别 3 次，按缩放后字形大小分组：

| 缩放后字形 | 3 次准确率 | 表现 |
|---|---|---|
| 17px | 98% / 97% / 96% | 稳定 |
| 11px | 10% / 83% / 79% | **波动 72 个百分点** |

结论：低于可靠阈值时，模型不是"稍微差一点"，而是**有时编、有时蒙对**。
所以提醒门槛（15px）刻意比切片门槛（12px）严格 ——
两边的代价不对称：误报只是多一句提示，漏报则是**静默交付编造的数据**
（实测把"复印纸"读成"密封圈"，任务却是绿色的"成功"）。

### 提醒必须传到用户眼前

引擎的 warnings 原先**只存在于 OcrResult 里**，动作返回的 TaskResult 只带一句摘要，
于是被静默丢弃。现在 `summarize_with_warnings` 会把提醒写进任务摘要并记入日志：

```
1 张表 · 27 行 · ⚠ 字号偏小（缩放后字形约 13px，低于可靠的 15px），
识别结果可能不准确甚至出现编造内容 —— 建议把表格拍得更近、更清晰后重试
```

## 四、回归保护

新增 `core/tests/test_table_recognition.py`（51 项），锁住本轮修掉的每一处：

| 分组 | 覆盖 |
|---|---|
| 检测结构兼容 | 裸多边形 / 三元组 / 垃圾输入；**端到端断言 `detect_lines` 必须有框** |
| 行高与切片 | 自适应分位数、上下限夹取、**不缩小就不切片**、表格不竖切 |
| 表格片段合并 | 同表拼接、接缝去重、不同表不混、不做全局去重、千分位算差异 |
| 内容裁边 | 找到内容区、非白背景、无可裁时不裁、空白图、极小图 |
| 数值与格式 | 14 组值与格式用例；货币列必须是数字 |
| 提醒透传 | 摘要含警告、日志逐条、无警告时不改动 |

其中 `test_detect_lines_actually_returns_boxes` 是**端到端**的：
它如果失败，说明"行高测量"整条链路又断了 —— 而它断了不会报错，
只会让切片决策退回瞎猜。

> 教训：那个检测 bug 能潜伏这么久，就是因为**没有任何测试碰过
> `detect_lines` 的真实返回值**。tiling 的 24 项测试全部在测
> `plan_tiles` 这类纯函数，输入是手工构造的 TextBlock，绕开了唯一会出错的环节。

## 五、遗留

* **评测用例是合成的**，不是真实用户文件。它能证明"管线正确"，
  但不能覆盖所有真实版式（跨页表格、嵌套表头、竖排文字等）。
  建议后续拿真实脱敏文件补充用例。
* 缩放后字形低于约 12px 时模型会**编造内容且不稳定**（实测波动 72 个百分点）。
  当前的处理是**明确提醒用户重拍**，而不是假装能给出可靠结果。
* 极端宽表（宽度远超 1300px 且文字很小）只能靠裁边缓解；
  按列切片并横向合并表格片段成本较高，暂未实现。
