## 2. 本轮修掉的缺陷

M7 过程中一共发现并修复 **11 个缺陷**，其中 3 个是"用户会真的遇到、但很难自查"
的类型。按严重程度排列：

### 2.1 【严重】失败的 COM 调用会泄漏 Office 进程，且永久失联

**现象**：开发机上发现 6 个无主的 `WINWORD.EXE`，关掉应用也清不掉。

**定位**：`ComAppWorker._invalidate()` 只把应用引用置空、**不同步杀掉进程**。
于是每次调用失败都留下一个孤儿；更糟的是下次 `_get_app()` 会把
"启动前已存在的进程"整体记为 `_foreign_pids`（外来进程＝永不触碰），
那个孤儿从此**不在 `_owned_pids` 里，任何清理逻辑都认领不到它** ——
连进程退出时的兜底清理也救不回来。

**复现**（诊断脚本，连续 4 次失败）：

```
基线 WINWORD: []
第 1 次调用按预期失败 → WINWORD: [27476]
第 2 次调用按预期失败 → WINWORD: [27476, 28348]
第 3 次调用按预期失败 → WINWORD: [27476, 28348, 7768]
第 4 次调用按预期失败 → WINWORD: [27476, 28348, 7768, 11452]
shutdown_all() 后 WINWORD: [27476, 28348, 7768, 11452]   ← 一个都清不掉
```

**修复**：`_invalidate()` 改为"先释放代理 → 再杀进程"；并在 `_get_app()`
里加一道兜底清理（**在记录 `_foreign_pids` 之前**），确保任何遗留进程都不会
变成"外来进程"。修复后同样的脚本：全部为 `[]`。

**回归用例**：`test_doc_convert.py::test_failed_call_does_not_orphan_a_word_process`。

### 2.2 【严重】流水线会产出"内容是 PDF、后缀是 .docx"的文件

任务队列在**开工前**用 `ActionSpec.output_ext` 定好输出文件名。流水线的输出类型
却取决于**最后一步**，沿用源文件的扩展名就会产出一个双击打不开的文件。

**修复**：给 `ActionSpec` 加动态钩子 `output_ext_fn`，队列改用
`spec.resolve_output_ext(params)`。流水线的钩子读最后一步的 `output_ext`。

**回归用例**：`test_pipeline.py::test_pipeline_job_output_extension_follows_last_step`
（走真实队列，断言产物后缀是 `.pdf` 且能被 PyMuPDF 打开）。

### 2.3 【中】CLI 的 watch 只能处理第一批文件

第一版实现每批任务都调用一次 `asyncio.run()`。`JobManager` 是模块级单例，
而 `shutdown()` 会把线程池永久关闭 —— 于是第二批任务必然报
`cannot schedule new futures after shutdown`。实测第一批成功后，
第二批 3 个文件全军覆没。

**修复**：`JobManager` 的线程池改为惰性创建/可重建（`_ensure_pool`），
watch 整个会话共用**一个**事件循环与一个管理器。

**回归用例**：`test_cli.py::test_repeated_runs_share_singleton_manager`、
`test_run_job_twice_in_one_loop_after_shutdown`、
`test_watch_processes_files_arriving_in_later_waves`（三波文件，含运行中新增）。

### 2.4 【中】COM 代理跨线程释放，日志里出现莫名的 "Windows fatal exception"

两种码交替出现，都是 SEH（不是 Python 异常，`try/except` 拦不住）：

* `0x800401f0`（CO_E_NOTINITIALIZED）：异常对象带着 traceback 一起被存进
  Future，traceback 的栈帧持有 `app`；Future 可能在**别的线程**上被回收，
  COM 代理的 `Release()` 就发生在没有 `CoInitialize` 的线程上。
* `0x800706ba`：反向问题 —— 释放时服务器已经被杀了。

**修复**：把清理顺序固定为 **丢掉本线程引用 → 摘掉 traceback → 释放并杀进程**，
保证最后一个引用始终在创建它的工作线程上、且**服务器还活着**时释放。
修复后 `test_doc_convert.py` 的 stderr 从 3~6 段堆栈降到 **0**。

### 2.5 【中】流水线里出错不说是第几步

动作自己抛的 `ActionError`（如"页码范围「99-100」没有匹配到任何页面"）
被原样向上抛。单看很清楚，放进 5 步流水线里就完全不知道是哪一步的问题。
**修复**：统一包一层 `第 N 步「动作名」失败：...`（`ActionCancelled` 除外，
取消不是失败）。

### 2.6 【轻】界面里「任务历史」挂着一个过期的「M7」未实现角标

该功能在 M2/M3 就已经做完，角标却还在，会让人以为点了没反应。已移除。

### 2.7 【轻】`parse_param` 允许空参数名

`--param "=value"` 会被静默忽略，用户只看到"参数没生效"却找不到原因。
**修复**：空键直接报错。

### 2.8 【轻】`_quit_app` 在杀进程后才释放代理

`Release()` 向已死的服务器发 RPC → `0x800706ba`。**修复**：先解引用再杀。
（这是 2.4 的同源问题，在退出路径上的另一处表现。）

### 2.9 【轻】README 里写的 npm 脚本在 Windows 上跑不起来

`package.json` 的脚本写的是 `core/.venv/Scripts/python.exe`（正斜杠）。
pnpm 在 Windows 上通过 `cmd.exe` 执行脚本，cmd 会把 `core/.venv/...`
当成命令名，直接报 `'core' is not recognized`。也就是说
**README 里推荐的 `pnpm package:win` / `pnpm core:test` 一直是坏的** ——
本轮真正去跑打包命令时才暴露出来（此前一直是手敲等效命令）。
**修复**：脚本改用反斜杠。本项目是 Windows 专用形态（NSIS 安装包、
Office COM 自动化、DPAPI 密钥存储），用 Windows 路径是正确的选择，
不必为了形式上的跨平台写成不可读的样子。

### 2.10 【严重】CLI 在普通 Windows 控制台上会直接崩掉

**现象**：打包后的 `docforge-core.exe selfcheck` 抛
`UnicodeEncodeError: 'gbk' codec can't encode character '\u2713'` 然后整个进程退出；
`docforge-core.exe pipeline ...` 产物已经生成，却返回退出码 **1**。

**原因**：Windows 控制台默认代码页是 GBK（cp936），而 CLI 会打印
`✓` `✗` `→` 这类符号，GBK 编不出来，`print` 直接抛异常。
用户在 cmd 里手敲 `docforge run ...` 时**不会**先设置 `PYTHONIOENCODING`，
所以这个坑一定会踩到 —— 而且表现是"批量处理跑到一半崩掉、只留下半批产物"，
比符号显示不全糟糕得多。

之所以此前的 CLI 手工验证没发现，是因为测试时一直带着
`PYTHONIOENCODING=utf-8`，**测试姿势本身把这个缺陷挡住了**；
而打包后的可执行文件连这个环境变量都不认，于是它在打包验证里露了头。

**修复**：新增 `cli.configure_stdio()` —— 把控制台输出代码页切到
UTF-8（65001），并把所有输出流的 `errors` 设为 `replace`。
最差情况也只是个别符号显示成 `?`，不会让命令中途崩掉。

**回归用例**：`test_cli.py::test_cli_survives_a_gbk_console`
（以 `PYTHONIOENCODING=gbk` 起子进程跑 `selfcheck` / `actions` / `--version`，
断言退出码为 0 且 stderr 里没有 traceback）。

### 2.11 【轻】`pnpm core:test` 从仓库根跑不起来（13 个测试文件全部 collection error）

`python -m pytest core/tests` 在仓库根执行时，CWD 是仓库根，而 `docforge`
包在 `core/` 下，于是 13 个测试文件全部 `ModuleNotFoundError: No module named 'docforge'`。

之所以一直没发现：本机测试都是在 `core/` 目录下敲 `python -m pytest`，
而 **`python -m pytest` 会把 CWD 塞进 `sys.path`** —— 恰好掩盖了这个问题。
这已经是本轮第二个"测试姿势掩盖缺陷"的例子（另一个是 2.10）。

**修复**：在 `core/pyproject.toml` 里加 `pythonpath = ["."]`
（pytest 会相对 rootdir 解析，即 `core/`）。这样无论从哪个目录调用都成立。

> 这两件事说明一个规律：**验证命令必须用文档里写的那一条**。
> 手敲"等效命令"跑通，不等于用户按文档操作也能跑通。

### 另附：测试卫生

测试进程不走内核的 `__main__` 退出清理路径，因此用过 COM 的用例会在开发机上
留下无主的 `WINWORD.EXE`（实测跑完 `test_doc_convert + test_pipeline` 后残留 1 个）。
现在 `JobManager.shutdown()` 会顺手回收 Office 进程，`conftest.py` 也在会话结束时
兜底清理一次。**跑完全套 350 项后 WINWORD 计数为 0。**

> 顺带说明：`_invalidate()` 的修复不能只靠"退出时清理"来兜底 ——
> 因为孤儿进程会被误记为外来进程，一旦失联就**再也清不掉**。
> 这正是它比普通的进程泄漏更严重的地方。

## 5. 遗留与不做的事

* **云端 OCR 仍未用真实 API Key 联调**（用户侧没有 Key）。请求构造与错误处理
  按官方文档实现且有测试覆盖，但这是当前最主要的验证缺口，README 里如实标注。
* **「监听文件夹」只做在 CLI**。它天然是常驻进程，而内核随应用启停；
  要放进界面就得把内核改成常驻服务，与"本地优先、用完即走"的形态冲突。
  与其做一个关掉应用就失效的假开关，不如老实留在 CLI 里。
* PDF 加密 / 解密 / 权限设置仍未实现。
* 渲染进程包未做代码分割（1.41 MB）。本地加载，首屏实测无感知；
  强行分包会引入动态 import 的加载态与失败路径，收益不划算。
