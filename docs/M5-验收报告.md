## 1. 交付内容

### 1.1 PDF 水印（需求 4）

**矢量文字，而不是贴图。** 水印通过 PyMuPDF 的 `insert_text` 直接写进页面内容流，
好处有三：任意缩放都清晰、文件体积小得多（实测 4 页 PDF 加水印后仅 2 KB）、
**文字仍然可以被复制与检索**。若先渲染成位图再贴上去，用户就选不中它了。

界面提供：文字/Logo 水印、九宫格定位、平铺整页、**画布拖拽定位**、
不透明度、任意角度旋转、描边、页码范围、覆盖在正文之上或作为底纹、
模板变量（`{page}` `{pages}` `{filename}` `{date}`）、元数据水印。

### 1.2 两个实测踩出来的关键结论

**① 旋转页面的坐标语义有歧义。**

实测 `rotation=90` 的页面：按 `page.rect`（可见坐标）插入文字时，
放在可见矩形右下角的内容**没有出现在页面上**（落到了页面外）。
四种旋转角逐一测试后确认，插入类 API 在旋转页面上会得到意外的落点。

采用的解法是**临时归零旋转**：记下原旋转角 → `set_rotation(0)` →
此时 `rect` 与 `mediabox` 一致、坐标无歧义 → 打水印 → 恢复原旋转角。
水印写进页面内容流，会随页面一起旋转显示，视觉效果完全正确。
该策略对 0/90/180/270 四种旋转全部实测通过，并写成了回归测试。

**② `insert_text` 的 `rotate` 只接受 90° 的倍数。**

任意角度靠 `morph=(固定点, 变换矩阵)` 实现。把固定点设为水印中心后，
定位逻辑就能统一按"中心点"来算 —— 这也让几何模块的接口更干净
（只需要一套中心点约定，不必让每个调用方各自推导）。

### 1.3 PDF 工具箱

| 动作 | 说明 |
|---|---|
| `pdf.merge` | 按顺序合并，可选生成书签；**单个坏文件被跳过而不是让整批失败** |
| `pdf.split` | 按每 N 页或自定义区间拆分，产物归入以源文件命名的子目录 |
| `pdf.extract_pages` | 提取指定页面为新 PDF |
| `pdf.rotate` | 在**已有旋转角基础上叠加**，不会把用户原本的旋转覆盖掉 |
| `pdf.compress` | 字体子集化 + 图片降采样 + 流压缩；新 API 做能力探测，老版本自动降级 |
| `pdf.to_images` | 渲染为 PNG/JPEG，DPI 可选；JPEG 自动转 RGB 去掉透明通道 |
| `pdf.info` | 页数、尺寸、元数据、文字与图片统计，并**识别疑似扫描页** |

### 1.4 动作模型的一次扩展：聚合动作

合并是**多文件进、单文件出**，与"每个文件一个输出"的既有模型不兼容。
硬套会出现两个问题：用户拿到一堆无意义的中间产物；并发执行时多个任务争抢同一个输出文件。

因此给动作注册表加了 `aggregate` 标记：这类动作把整批文件当作**一个**任务，
handler 通过 `ctx.files` 读取全部输入，输出名走 `aggregate_name` 模板
（例如 `合并结果_2个文件.pdf`）。

### 1.5 界面

- **PDF 水印页**：服务端实时预览 + 页码滑杆 + 扫描件提示 + 画布拖拽定位
- **PDF 工具箱页**：7 个工具，参数表单**完全由后端 `paramsSchema` 自动生成**，
  新增工具只需在内核注册动作 + 前端加一行图标配置
- 界面明确区分「合并模式（整批一个结果）」与「逐个文件处理」，
  避免用户选了合并却以为只处理了第一个文件

### 1.6 预览仍是"同源渲染"

预览接口调用的是**与正式任务完全相同的** `apply_pdf_watermark`，
只是把页码范围限定到预览的那一页。因此不存在"预览和结果不一致"的可能。
（这也是 M3 定下的原则：前端一旦自己复刻排版逻辑，字体度量与坐标舍入的细微差异
迟早会让用户看到"预览好看、结果不对"。）

## 3. 验证方法上的一次教训

第一轮 UI 验证时，我先用视觉模型去看预览图，它回答"页面上没有水印"。
**这个结论是错的。**

改用**程序化像素对比**（渲染无水印页面 vs 已加水印页面，逐像素求差）后得到：

```
[界面默认参数] 有差异
    差异区域 bbox = (335, 512, 495, 657)  页面尺寸 = (827, 1170)
    明显变化像素 = 13637 (1.41%)
    是否完全落在页面内：是
矢量文字 '机密' bbox=(244.3,367.2)-(355.1,468.6)   page.rect=595×842
```

换算出渲染坐标 339–493，与差异区域 335–495 完全吻合 —— 水印位置正确、完整在页内。

原因是水印默认 32% 不透明度、浅红色，在白色背景上对比度很低，视觉模型没能识别出来。
**教训：低对比度、细微几何位置这类判定，必须用可量化的程序化手段验证，
不能依赖视觉模型的"看图说话"。** 这已经是本项目中视觉模型第二次给出不可靠结论
（M2 时它把桌面应用截图描述成了聊天软件）。

## 4. 一处未复现的异常（如实记录）

验证过程中，工作区里出现过一次来自微信临时目录的 PNG，
同时路由跳到了「图片转 Excel」页。我做了决定性测试：**不带任何文件参数重启应用，
工作区保持 0 个文件，长时间观察也无自发导入**；随后带 PDF 参数重启，工作区正好 2 个文件。
均未能复现。

结论：这最可能是一次**真实的拖拽投放事件**（应用正确接收了被拖入的文件），
而不是自动导入缺陷 —— 代码里没有任何"扫描目录/自动导入"的路径。
如实记录在此，若后续再次出现会进一步排查。
